# EaC v0.3

EaC v0.3 introduces deterministic Reactive Experience while preserving the existing Timed model.

v0.1 and v0.2 were built on `value = f(time)`. v0.3 adds `value = f(time, signals)` without giving up
reproducibility. The two property kinds carry different — and precisely stated — guarantees:

- **TimedProperty is directly seekable.** Evaluating at time `t` requires no history.
- **ReactiveProperty is deterministically replayable.** Evaluating at `t` replays an explicit input
  scenario from the declared initial state, and always yields the same result.

These are not the same guarantee, and this document never treats them as if they were. Timed
semantics were not weakened to accommodate reactive ones.

The full implemented specification is [`docs/spec/v0.3.md`](spec/v0.3.md).

## Highlights

**Signal model.** A closed, typed registry of everything a reactive expression may read: `pointer.x`,
`pointer.y`, `pointer.down`, `pointer.present`, `scroll.x`, `scroll.y`, `viewport.width`,
`viewport.height`, `key(code)`, `hover(node)`, `pressed(node)`, and declared state. Every value is a
`number` or a `boolean`. `hover` and `pressed` are derived from scene geometry, not read from the
host, so "the pointer is over this card" has a definition rather than a browser behaviour.

**State.** `scene.state(name, initial)` declares named, serializable `boolean` or `number` state with
an explicit initial value. It is what replay starts from and what assertions read.

**ReactiveProperty bindings.** `scene.bind(node, { … })` drives position, scale, rotation, opacity,
depth, blur, and fill/stroke colour mixing from expressions. One binding owns one whole property, at
the same granularity the v0.2 single-writer rule already uses.

**Closed Reactive Expression IR.** The authoring helpers — `when`, `clamp`, `lerp`, arithmetic,
comparison, boolean operators — are constructors that return inert IR. Nothing captures a closure, so
bindings serialize, type-check, print back into diagnostics, and can be traversed safely. There is no
`eval` and no `new Function` anywhere in the runtime.

**Explicit EventRule / Action model.** Rules are data: `{ id, trigger, guard?, actions[] }`. Triggers
are `pointerEnter`, `pointerLeave`, `pointerDown`, `pointerUp`, and `click` on a node; `keyDown` and
`keyUp` on a code; and `scroll`. Actions are `setState`, `toggleState`, and `playSound`. No callbacks
survive into the IR, so `eac inspect` can print every rule and the checker can reason about them.

**Deterministic hit testing.** The pointer is transformed into node-local space by the inverse world
matrix, so rotation, scale, and nested group transforms are exact rather than approximated by a
bounding box. `interactive: false` opts a decorative node out.

**Hover, click, keyboard, and scroll.** All four are derived by the runtime from normalized input,
never reported by the host.

**Versioned ScenarioIR.** A scenario is JSON-serializable data with `version` and `scenarioVersion`:
a duration, optional initial pointer and scroll, timestamped events with a strictly increasing global
`order`, and assertions.

**Assertions.** A scenario can pin state values, hover, and approximate property values, which turns
a recorded interaction into an integration test that `eac check` runs.

**`ExperienceSession` replay and checkpoints.** One session serves the checker, the inspector, the
renderer, and the browser. It snapshots replay state periodically and resumes from the nearest
snapshot; caching is an optimization only.

**Live browser preview using the shared runtime.** Pointer, keyboard, and wheel input drive reactive
output as you interact.

**Recording → replay → export.** The live session and the recording read one normalized input stream,
so an exported scenario is by construction the interaction that just happened.

**`eac render --scenario`.** Renders a scenario to a deterministic MP4.

**Reactive event-triggered audio.** `scene.sound(id, path)` declares a clip with no start time;
`playSound` records `{ sound, at }` at the triggering step, and the encoder muxes those records as
ordinary clips.

**Tooling.** `eac check --scenario` reports replay steps, semantic events, state transitions, and
assertion outcomes. `eac inspect --scenario` prints signals, state, bindings, rules, and the full
transition history, with a matching `--json` snapshot. `eac docs` gained fourteen searchable reactive
and interaction topics.

## Core architecture

```text
live input
  → normalized EaC event
  → shared ExperienceSession
  → reactive / timed evaluation
  → EvaluatedScene
  → SVG preview / render
```

```text
recorded input
  → ScenarioIR
  → deterministic replay
  → check / inspect / video render
```

**There is no second browser-specific reactive evaluator.** `@eac/runtime` and the SVG renderer's
pure lowering path are bundled into one self-contained script that the preview page loads; the page
is a driver around them. Hit target, pressed target, whether a click occurred, state transitions, and
every reactive value are decided by the same `ExperienceSession` that `eac check`, `eac inspect`, and
`eac render` use. DOM events are input only.

A conformance test executes that exact bundle and compares evaluated scenes, replay state, and
rendered SVG against the Node session at every semantic transition in a representative trace.

See [ADR 0014](adr/0014-shared-semantic-runtime-in-the-browser.md).

## Determinism model

- **Semantic time is frame-based.** Time is derived from the frame index as `frame / fps`.
- **The browser wall clock only schedules painting.** `requestAnimationFrame` decides _when_ a frame
  is displayed, never _what_ it contains. Pause, seek, and frame-step stay exact.
- **Input is quantized to frame boundaries.** Live input is buffered and committed at a frame, which
  is exactly how scenario replay applies it.
- **Same source + assets + initial state + scenario + runtime version produces the same result.**
  No wall clock, no unseeded randomness, no network, no ambient host state in experience semantics.
- **Cached and fresh replay are semantically equivalent.** `replayFresh` replays from zero with no
  cache, and tests assert it agrees with the checkpointed path at every probed time, including under
  scrambled seek order.

## Interaction semantics

Each replay step freezes the interaction geometry _before_ hit-testing it, using the state committed
by the previous step. That removes every same-instant feedback loop: a hover-scale binding resolves
into a documented one-step reactive lag rather than an oscillation.

- Click is derived from down and up resolving to the same target; moving off the target in between
  produces no click.
- The topmost target is the highest world depth, then latest declaration order, then node id — the
  exact reverse of paint order.
- There are no DOM bubbling or capture semantics. One point resolves to one target.

Formal details live in [`docs/spec/v0.3.md`](spec/v0.3.md) §6–§8 and in
[ADR 0009](adr/0009-frame-phase-model-and-hover-stability.md),
[ADR 0010](adr/0010-hit-testing-and-target-resolution.md), and
[ADR 0013](adr/0013-event-rules-and-state-transitions.md).

## Scenario workflow

```text
Live → Record → Stop → Replay → Export → Check / Inspect → Render MP4
```

Interact with the experience, record the interaction, replay it to confirm it is what you meant,
export it as a scenario file, then check and inspect it and render it to video — with no edits to the
source in between.

`ScenarioIR` is **inert data, not executable JavaScript**. A `.json` scenario is parsed and validated;
it is never imported or evaluated. A `.mjs` builder is accepted for authoring and produces the same
IR. Accepting a scenario from a colleague, a fixture directory, or an agent runs no code.

## Browser preview

The preview is live. The following now work while you interact, through the same
`ExperienceSession` the Node-side tooling uses:

- **pointer** — movement normalized into scene coordinates
- **hover** — derived by hit-testing that geometry
- **click** — derived from down and up, not reported by the DOM
- **keyboard** — normalized to layout-independent key codes
- **scroll** — wheel input mapped to explicit scroll signals

Controls: Play, Pause, Reset, frame back and forward, a time scrubber, a Live/Replay mode indicator,
Record, Stop, Replay recording, and Export scenario. A debug panel shows time, frame, hovered target,
pressed target, state, signals, recent semantic events, and the transition history.

The page is a single self-contained file: no server, no CDN, no network.

**Preview audio remains intentionally silent.** `playSound` actions still appear in the semantic
event and transition history, and `eac render` muxes them into the MP4.

- `interactive-showcase`: 0 errors / 0 warnings, live and under its canonical scenario
- browser/Node semantic conformance verified — identical evaluated scenes, replay state, and
  rendered SVG at every probed transition
- record → replay equality verified frame by frame, not only at the end
- deterministic rendered artifacts verified: repeated renders of the same source and scenario produce
  byte-identical PNG and MP4 output
- format, lint, strict typecheck, and build pass
- `pnpm audit --audit-level high`: no known vulnerabilities
- `pnpm bench:verify-public` passes

Performance is tracked only by loose regression sentinels. No hardware-independent performance
guarantee is claimed.

## Compatibility

- Existing Timed APIs remain valid.
- All v0.2 examples continue to pass unchanged. A scene with no reactive content produces an empty
  override set and evaluates exactly as it did in v0.2.
- `ExperienceIR` carries `version: "0.3"` and `irVersion: 3`. Serialized v0.1 and v0.2 IR are refused
  with a diagnostic naming the version found; they are never reinterpreted.
- **SimulatedProperty remains unsupported** and fails explicitly.
- Historical `benchmark-v0.1-main-r3` evidence remains unchanged. The tag still points at
  `e4e69417f701e0944f1ae4aa8db1017efb9828c0`, and `bench/results/r3` and `docs/benchmark-r3.md` are
  identical to their published form. The v0.1 experiment was not rerun.

## Limitations

- Preview audio is silent.
- Input is frame/FPS quantized, so changing `fps` can shift an interaction by up to one frame.
- Reactive output has a one-step delay by design; this is what makes hover stable.
- Events cannot start Timed animations yet.
- Event payloads are not exposed to rules, so "click at x, y" is not expressible.
- Path hit testing uses the node-local axis-aligned bounding box.
- Text hit bounds use a deterministic advance-width approximation, not real glyph metrics.
- There is no focus system; keyboard is a global signal set.
- There is no bubbling or capture; one point resolves to one target.
- There is no multitouch.
- There is no SimulatedProperty and no physics.

## What v0.3 proves

v0.3 demonstrates that an EaC experience can be interacted with live, recorded as an explicit
scenario, replayed deterministically, inspected and checked, and rendered to video using one shared
semantic runtime.

That is the claim, and it is bounded. EaC remains an experimental runtime for studying deterministic,
verifiable experiences as code. It is not a replacement for a browser UI framework, and nothing here
argues that it is.

## Next direction

Likely v0.4 work, in rough order of demand:

- explicit Timed + Reactive composition, replacing today's refusal with a named combination rule
- event-triggered Timed animation, the feature that most often runs into that refusal
- richer event payloads for rules
- focus and accessibility foundations
- a v0.3-specific agent benchmark, designed for reactive authoring rather than reused from v0.1
- SimulatedProperty eventually, but not yet
