# EaC v0.3 specification — Reactive Experience

Status: implemented semantics. Everything described here exists in the repository and is covered by
tests.

v0.1 and v0.2 were built on `value = f(time)`. v0.3 adds `value = f(time, signals)` without giving
up reproducibility.

## 1. The evaluation contract

```text
experience source + assets + runtime version + initial state + input scenario + t
  → deterministic evaluated experience
```

Forbidden in experience semantics: wall clock, unseeded randomness, network access, ambient browser
or device state, implicit pointer/focus/scroll read from the host, and event listeners outside the
runtime input adapter. The browser adapter is an input source, never a semantic source.

## 2. Property taxonomy

```ts
type Property<T> = TimedProperty<T> | ReactiveProperty<T> | SimulatedProperty<T>;
```

- **TimedProperty** — shipped in v0.1. **Directly seekable**: evaluating at `t` needs no history.
- **ReactiveProperty** — shipped in v0.3. **Deterministically replayable**: evaluating at `t`
  replays the explicit scenario from the initial state up to `t` and always yields the same result.
- **SimulatedProperty** — still unsupported. `eac::property::simulated-unsupported`.

These are not the same guarantee and the docs never conflate them. Timed semantics were not weakened
to accommodate reactive.

## 3. Signals

A closed, typed registry. Every value is `number` or `boolean`.

| Signal | Type | Source |
| --- | --- | --- |
| `pointer.x`, `pointer.y` | number | scenario input |
| `pointer.down`, `pointer.present` | boolean | scenario input |
| `scroll.x`, `scroll.y` | number | scenario input |
| `viewport.width`, `viewport.height` | number | scenario input |
| `key(code)` | boolean | scenario input |
| `hover(node)` | boolean | derived by hit-testing |
| `pressed(node)` | boolean | derived from the press gesture |
| `state(name).value` | number \| boolean | declared state |

`hover` and `pressed` have a geometric definition, not a host one. Raw DOM events never appear in the
IR.

## 4. Expression IR

A closed vocabulary, all inert data, no closures and no `eval`:

```text
const  signal
add sub mul div min max neg
eq neq lt lte gt gte
and or not
conditional  clamp  lerp
```

Typing is total over the vocabulary and runs before rendering. Every traversal is cycle-safe: raw IR
can contain a self-referential expression graph, so typing, evaluation, and signal collection stop at
a repeated node and the checker reports `eac::reactive::cycle` rather than overflowing the stack.

Cycles *between* bindings are structurally impossible under the phase model in §6, so the hover-scale
interaction is legal rather than circular. See ADR 0008.

## 5. State and event rules

```ts
const expanded = scene.state("expanded", false);
scene.bind(panel, { opacity: when(expanded.value, 1, 0) });
scene.on(onClick(button), toggle(expanded));
```

State is `boolean` or `number`, named, serializable, and has an explicit initial value. Rules are
data — `{ id, trigger, guard?, actions[] }` — never callbacks.

- Triggers: `pointerEnter`, `pointerLeave`, `pointerDown`, `pointerUp`, `click` on a node;
  `keyDown`, `keyUp` on a code; `scroll`.
- Actions: `setState`, `toggleState`, `playSound`.

See ADR 0013.

## 6. Frame phase model

The replay timeline is the ordered merge of **frame ticks** at `k / fps` and **scenario events**,
sorted by `(time, rank, order)` with `rank` 0 for ticks and 1 for events. `order` is a strictly
increasing global sequence assigned at build time, so ties are impossible.

Each step runs seven phases:

1. **Freeze interaction geometry** from TimedProperties at the step's time and bindings evaluated
   with the state committed by the *previous* step.
2. **Apply raw input** — a scenario event updates pointer, buttons, keys, or scroll; a tick does not.
3. **Hit-test** the pointer against the geometry frozen in phase 1.
4. **Derive semantic events** in the fixed order `pointerLeave`, `pointerEnter`, `pointerDown`,
   `pointerUp`, `click`, `keyDown`, `keyUp`, `scroll`.
5. **Evaluate rules** — matching rules run in declaration order; guards read the state as it stood at
   the start of the step.
6. **Commit state atomically** — two writes to one state in one step are an error, never a race.
7. **Recompute reactive output** from the committed state.

Evaluating at a non-step time replays every step up to it, then evaluates TimedProperties at exactly
the requested time. Timed motion stays continuous; reactive state is a step function of steps.

**Hover stability**: because phase 1 precedes phase 3, hover in step *n* can never depend on hover in
step *n*. A hover-scale loop becomes a documented one-step lag, not an oscillation. Interaction is
sampled at `fps`, so preview and rendered video agree exactly. See ADR 0009.

## 7. Click semantics

`pointerDown` records the hit target as `pressed`. `pointerUp` emits `click` only when the current
hit target equals the pressed target. Moving off the target between down and up produces no click.
No browser click quirks are involved.

## 8. Hit-testing

The pointer is transformed into node-local space by the inverse world matrix, then tested against the
node's own geometry — exact for rect, circle, and image; text uses the deterministic advance-width
box; path uses its local bounding box and is documented as approximate.

- Topmost target: highest world depth, then latest declaration order, then node id — the exact
  reverse of paint order.
- Leaves only; groups transform their children but are not targets.
- World opacity of zero is not hittable.
- `interactive: false` opts a node out.
- One target per point: no bubbling, no capture phase.

See ADR 0010.

## 9. Writer rules

A property is timed-driven or reactive-driven, never both:

- timed writer + reactive binding → `eac::reactive::mixed-property-writers`
- two reactive bindings on one property → `eac::reactive::mixed-property-writers`
- two writes to one state in one step → `eac::reactive::multiple-state-writers`

Granularity is the whole property, matching how `followPath` already claims the vector position
property. Different properties of the same node may mix freely, which is what the showcase does. See
ADR 0011.

## 10. Scenario format

`ScenarioIR` is JSON-serializable and versioned (`version: "0.3"`, `scenarioVersion: 1`): duration,
optional initial pointer and scroll, events, and assertions. `.json` files are parsed as data and
never executed; a `.mjs` builder is accepted for authoring and produces the same IR.

Assertions cover state equality, hover, and approximate property values, so a scenario doubles as an
integration test:

```bash
eac check scene.mjs --scenario trace.eac-scenario.mjs
```

## 11. Replay and checkpoints

`ExperienceSession` snapshots full replay state every 64 steps and resumes from the nearest snapshot.
Caching is an optimization only: `replayFresh` replays from zero with no cache, and a test asserts it
agrees with `replayTo` at every probed time. Seeking backward, forward, or repeatedly gives identical
results.

## 12. Reactive audio

`scene.sound(id, path)` declares a WAV clip with no start time. `playSound` records `{ sound, at }`
at the triggering step, and the encoder turns those records into ordinary audio inputs. There is no
WebAudio, no streaming, and no scheduling API. Reactive audio is exactly as replayable as the video.

## 13. Tooling

```bash
eac check   scene.mjs --scenario trace.mjs   # diagnostics, replay stats, assertions
eac inspect scene.mjs --scenario trace.mjs   # signals, state, bindings, rules, transitions
eac preview scene.mjs --scenario trace.mjs   # replay, record, export
eac render  scene.mjs --scenario trace.mjs   # deterministic interactive video
```

`eac inspect --json` remains stable structured JSON.

## 14. Live preview

The preview is **live**. Pointer, keyboard, and wheel input drive reactive output as you interact —
no export-and-reload step.

```text
browser DOM event
  → normalized EaC input (@eac/runtime/browser)
  → LiveSession / ExperienceSession        ← the same engine as check, inspect, and render
  → reactive + timed evaluation
  → evaluated scene
  → renderSvg
  → preview display
```

**The browser preview does not implement separate reactive semantics.** `@eac/runtime` and the SVG
lowering path are bundled with esbuild into one ~20 KiB self-contained script; the page is a driver
around them. A conformance test executes that exact bundle and compares evaluated scenes, replay
state, and rendered SVG against the Node session at every semantic transition. See ADR 0014.

- **DOM events are input only.** The page forwards `pointerMove`, `pointerDown`, and `pointerUp`. It
  never reports "this node was clicked"; the runtime derives hit target, pressed target, click, and
  every state transition.
- **Semantic time is the frame index**, `frame / fps`. `requestAnimationFrame` decides when to paint,
  never what a frame contains, so pause, seek, and frame-step stay exact.
- **Live input is quantized to frame boundaries**, exactly like scenario replay.
- **One input stream** feeds the live session and the recording, so an exported scenario is
  by construction the interaction that just happened. Replaying it in a fresh session reproduces it
  frame for frame — this is tested at every frame, not just at the end.
- **Modes**: Live and Replay, both through `ExperienceSession`. Record → Stop → Replay recording →
  Export walks a user from interaction to a committed fixture to a rendered video with no source
  edits.
- **Reset** restores time, signals, app state, hover and pressed targets, event and transition
  history, the recording, and the replay cursor.
- **Offline and network-free**: one HTML file, no server, no CDN, no `eval`, no `new Function`.

Preview remains silent (§12). `playSound` actions still appear in the transition history, and
`eac render` muxes them.

## 15. Compatibility

`ExperienceIR` carries `version: "0.3"` and `irVersion: 3`. Serialized v0.1 and v0.2 IR are refused
with a diagnostic naming the version found; they are never reinterpreted. TypeScript v0.2 sources
rebuild into v0.3 IR unchanged, and every v0.2 example still passes `eac check --ci`. A scene with no
reactive content produces an empty override map and evaluates exactly as it did in v0.2.

## 16. Security

Scenario files are data. Reactive expressions are constrained IR. There is no `eval`, no
`new Function`, and no shell or network behaviour reachable from an event action. Asset path safety
is unchanged from v0.2: project-relative only, validated lexically and after `realpath`.

## 17. Not in v0.3

SimulatedProperty, physics, property composition, a second renderer, path tangent/orient-to-path,
pointer capture and bubbling, keyboard focus, multitouch, non-WAV audio, waveform analysis, audio
playback inside the preview, and accessibility roles.
