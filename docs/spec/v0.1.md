# EaC v0.1 実装指示書

## Codex / Claude Code 向け

## 0. この文書の目的

この文書は **EaC — Experience as Code v0.1** を実装するCoding Agent向けの実装仕様書である。

v0.1は完成プロダクトではない。

目的は、

> **Coding Agentが未知のDSLをCLIから学習し、EaCの検証結果を使って自己修正できるかを測るための、最小かつ実行可能な測定基盤を作ること。**

である。

成果物の派手さは評価対象ではない。

v0.1では以下を優先する。

1. DSLが小さく一貫している
2. IRがEaCの将来設計を壊さない
3. `eac help / guide / docs search` がAgentにとって有用
4. `eac check` が実際のミスを検出する
5. 同じSourceから同じ結果を再現できる
6. ベンチマーク可能である

---

# 1. EaCの基本思想

EaCはAI Agentではない。

Codex、Claude Code、その他Coding Agent、人間がEaCを使用する。

```text
User / Coding Agent
        ↓
      EaC DSL
        ↓
    Experience IR
        ↓
      Checker
        ↓
     Renderer
        ↓
 Web Preview / Frames / Video
```

EaCの原則：

> **Code is the source. Experience is the output.**

> **Pixels are output, not source.**

> **Creative software should be testable.**

> **Everything that changes is a function of inputs. Time is the input we can seek.**

---

# 2. Property Model

将来を見据え、Propertyは概念上3種類に分ける。

```ts
type Property<T> =
  | TimedProperty<T>
  | ReactiveProperty<T>
  | SimulatedProperty<T>
```

## TimedProperty

```text
value = f(time)
```

任意時刻を直接評価できる。

特徴：

* seekable
* deterministic
* harnessで任意時刻を検査可能
* v0.1の唯一の対応Property

---

## ReactiveProperty

```text
value = f(signals)
```

例：

* hover
* click
* pointer
* scroll
* microphone
* application state

v0.1では**未対応**。

入力された場合は明示的にエラーにする。

---

## SimulatedProperty

```text
nextState = f(previousState, dt, inputs)
```

例：

* gravity
* collision
* cloth
* physics spring

v0.1では**未対応**。

入力された場合は明示的にエラーにする。

---

# 3. v0.1の保証

v0.1では以下を保証する。

### Seekability

すべての有効なPropertyは任意時刻 `t` で直接評価可能。

### Determinism

同じSource、設定、Assetからは同じ結果を得る。

### Single Writer

同一Propertyの同一時間区間に複数Writerを持つことは禁止する。

例：

```text
star.position

moveTo  2s ━━━━━━━━━━━━━ 5s
moveTo       3s ━━━━━━━━ 4s
              ^
              conflict
```

Composition Mode、offset、blend等はv0.1では実装しない。

将来的に制約を緩めることは可能だが、最初から曖昧にしない。

# 5. Renderer方針

v0.1はSVG Rendererを使用する。

```text
Experience IR
     ↓
 SVG Renderer
     ↓
 SVG String
     ↓
  resvg
     ↓
 PNG Frame
     ↓
  ffmpeg
     ↓
    MP4
```

Remotionは使用しない。

理由：

* React依存を避ける
* Chromium依存を避ける
* EaC IRへ他ライブラリのTimeline概念を漏らさない
* 最小構成で検証する

---

# 6. IR ↔ Renderer 境界

v0.1のRenderer Interfaceは**暫定仕様**とする。

SVG Rendererのみで完璧な抽象化を設計しないこと。

原則：

> **Renderer abstraction should be reviewed once a second renderer exists.**

将来Canvas等の2つ目のRendererを実装する時点で、一度だけRenderer境界を再評価する。

ただし、v0.1時点でもSVG固有概念をCore IRへ入れない。

禁止例：

```ts
fillRule: "evenodd"
svgPathNode: ...
svgTransform: ...
```

CoreではPlatform NeutralなGeometry / Appearanceとして保持する。

# 9. Time Model

基本指定は、

```ts
{
  at: sec(2),
  duration: sec(1)
}
```

とする。

内部では、

```text
start = at
end = at + duration
```

に変換する。

無効例：

```text
duration <= 0
start < 0
end > scene duration
```

はChecker対象。

---

# 10. Current State Inheritance

Motionの開始値は基本指定しない。

例：

```ts
star.rotateTo(deg(180), {
  at: sec(3),
  duration: sec(2)
})
```

開始値は、

```text
star.rotation.at(3s)
```

をRuntimeが取得する。

つまり、

```text
newMotion.startValue
=
previousProperty.evaluate(startTime)
```

とする。

明示的な`from` APIはv0.1では不要。

# 15. Overlap Detection

v0.1のOverlap CheckはAABBのみ。

対応：

```text
Rect ↔ Rect
Rect ↔ Text bounds
Text ↔ Text bounds
```

必要ならCircle / PathもBounding Boxのみ利用可能。

非対応：

```text
Exact Path Intersection
Rotated Polygon SAT
Alpha-aware overlap
Pixel collision
```

診断にはApproximate Checkであることを表示してよい。

# 17. Multiple Writer Diagnostic

エラー識別子は番号を使わない。

例：

```text
eac::motion::conflicting-writers
```

診断形式は固定する。

必ず以下を含める。

1. **What** — 何が起きたか
2. **Where** — どこで起きたか
3. **Why** — なぜ問題か
4. **How** — どう直すか

可能な場合Timeline Visualizationも含める。

例：

```text
error[eac::motion::conflicting-writers]

`star.position` has multiple writers
between 2.0s and 4.0s.

moveTo  1.0 ━━━━━━━━━━━━━ 4.0
moveTo       2.0 ━━━━━━━━━━━━━ 5.0
             ^^^^^^^^^ conflict

Why:
EaC v0.1 allows only one writer per property
for any point in time.

Possible fixes:
- change one motion's `at`
- shorten one motion's `duration`
```

`offset`や`blend`はv0.1に存在しないため提案しないこと。

# 31. AGENTS.md

Repository Rootへ配置する。

内容：

````markdown
# Working on EaC

EaC is an experimental Experience as Code runtime.

## Before making changes

1. Read this file.
2. Read the current v0.1 implementation specification.
3. Run the test suite.
4. Keep v0.1 scope intentionally small.

## Core rules

- EaC is not an AI agent.
- v0.1 supports TimedProperty only.
- ReactiveProperty and SimulatedProperty must fail explicitly.
- A property may have only one writer at any given time.
- Do not introduce property composition in v0.1.
- Do not leak SVG-specific details into the core IR.
- Renderer abstraction is provisional until a second renderer exists.
- Error identifiers use namespaced strings, not numeric IDs.
- Diagnostics must explain what, where, why, and how to fix.
- Rendering must be deterministic.

## Architecture

Keep responsibilities separated:

- `core`: user DSL
- `ir`: platform-neutral IR
- `units`: value/unit types
- `checker`: validation
- `renderer-svg`: SVG rendering
- `cli`: command interface

Do not create large files that mix multiple responsibilities.

## Implementation style

- Prefer small, typed APIs.
- Prefer explicit errors over silent fallback.
- Do not add APIs not required by the current scope.
- Do not implement future features speculatively.
- Add tests for all checker rules.
- Keep examples minimal and deterministic.

## Before finishing a change

Run:

```bash
pnpm test
pnpm lint
pnpm typecheck
eac check
````

Fix the underlying issue instead of suppressing diagnostics.

````

実際のPackage Managerに応じてCommandは調整可能。
````

# 41. Hypothesis

v0.1の中心仮説：

> **Coding Agents can learn an unfamiliar creative DSL at runtime through a self-describing CLI and can converge toward valid output through structured diagnostics, without human correction.**

---

# 42. Hypothesis Rejection Criteria

結果が悪かった時の撤退線を事前に決める。

例：

固定5Taskのうち3Task以上でCondition Cでも、

* 未定義APIを繰り返し使用する
* `eac check`のDiagnosticを読んでも修正方向を理解できない
* 3回の修正Iteration以内に有効なEaCへ収束しない

場合、

> Primitive taxonomy、CLI Documentation、Diagnostic Designの少なくとも1つに根本的な設計問題がある

と判断する。

---

# 43. CLI Self-description Hypothesis

Condition BがCondition Aと比較して改善を示さない場合：

> `eac help / guide / docs search`による自己説明CLIという仮説を再評価する。

単に文言を無限調整して延命しない。

---

# 44. Check Loop Hypothesis

Condition CがCondition Bに対して自己修正成功率を改善しない場合：

> Agent-facing Diagnostic / Check Loopの設計を再評価する。

---

# 45. Public Release Criteria

最初の公開版はProduction Readyでなくてよい。

最低条件：

```text
✓ DSL compiles
✓ eac check works
✓ SVG preview works
✓ deterministic frame render works
✓ MP4 render works
✓ one Agent bench task completed
✓ experimental status clearly documented
```

ここまで来たら公開してよい。

# 47. Fixed Decisions

現時点で強く固定するもの：

### Property Model

```text
Timed
Reactive
Simulated
```

の概念分離。

### v0.x Single Writer Guarantee

同一Propertyの同時複数writerは禁止。

### Unit-aware API

時間、角度、長さ等を型として扱う。

### Agent-facing CLI

CLI自身が使い方を説明できる。

### Diagnostic Shape

```text
what
where
why
how
```

を必ず返す。

### Determinism

同じ入力から同じ結果。

# 61. Coding Rules

実装Agentは、

* 一気に全体を書かない
* Package単位で実装する
* 各Package完成時にtestする
* 公開APIには型をつける
* Checkerルールには必ずテストを書く
* Snapshotより意味的Assertionを優先する
* 未実装機能をsilent fallbackしない
* TODOでFuture Featureを疑似実装しない

こと。

# 63. 最後に

EaC v0.1の目的は、

> **Remotionより良い動画を作ることではない。**

> **完成したUI Frameworkを作ることでもない。**

最初に証明するのは、

> **未知のCreative DSLであっても、Coding AgentがCLIから使い方を学び、Compiler / Checkerからフィードバックを受け、正しいExperienceへ自己修正できるか。**

である。

その仮説が成立した後に、

```text
UI
Interaction
Audio
Motion Graphics
3D / Depth
Live Character
Cross-platform Rendering
```

へ拡張する。

EaCは最終的に、

> **人間とCoding Agentの両方が、検証可能で再現可能なExperienceをコードとして作るためのCreative Runtime**

を目指す。
